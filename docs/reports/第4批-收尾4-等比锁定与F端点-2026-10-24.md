## 二、`system-isolated`：真实的几何错位（不只是告警）

### 2.1 根因复核（你的诊断成立，且实际误差方向随容器而变）

斜面三角形是用 `w_px = slope_W * scaleX`、`h_px = slope_H * scaleY` 画的，而滑块与 N、f 矢量
是屏幕空间 `rotate(θ)`；二者只在 `scaleX === scaleY` 时重合。原代码

```
physicsWidth: 12, physicsHeight: 8   // 宽高比 1.5
```

塞进 splitV 的 840:325（2.58），必然非等比。实测容器 828×726（中屏真实尺寸）时：

| 量 | 改前 | 改后 |
|---|---|---|
| `scaleX` | 70.0 px/m | **67.2** |
| `scaleY` | 92.1 px/m | **67.2** |
| 斜面实渲倾角（θ=30°） | `arctan(92.1/70 · tan30°) = **37.2°**` | **30.0°** |
| 滑块角度 | `rotate(30°)`（与斜面差 7.2°） | 与斜面重合 |
| m₁ 方块 | 56 × 73.6 px（长条） | 53.8 × 53.8（正方形） |
| 斜面尺寸 | 252 × 191 px | 242 × 140 px |

> 注：你给的 18.5° 是「容器恰好 840×325」时的取值；本页中屏比预设高得多，
> 实际是把 30° **压陡**到 37.2°。方向相反、结论一致：只要有非等比，角度就不可信。

### 2.2 修法：反解统一比例尺，而不是给两个量程

```
scaleUniform = min( 设计宽 / NEED_WIDTH , (设计高 − 箭头余量) / 需要高度 )
physicsWidth  = 设计宽 / scaleUniform
physicsHeight = 设计高 / scaleUniform      // 二者之比恒等于 840:325
```

- `NEED_WIDTH = 12.5 m`：连接体最远滑到 x ≈ 10.1 m，再留 F 箭头与标签。
- `需要高度 = 斜面高 + 滑块 + 0.4 m`：**随 θ 变化**，所以 θ 越大整幅画面等比缩小，而不是拉变形。
  θ=60° 实测斜面 59.5°、顶部不裁切。
- `ARROW_TOP_PX = MAX_ARROW × 0.7 + 24`：最长竖直力箭（gravity / appliedForce 权重 0.7）加标签。
- 原点由 `originSource: 'custom'` 下移到「地面以下 0.4 m」：原来物理原点在 y=0，地面在 1.6 m 高，
  等于白占 1.2 m 画布高度，等比锁定时会把整个场景压小 20%。
- 几何常量收进 `SCENE_GEOM`（`groundY / slopeWidth / blockSize`），量程、model1、model2 共用一份，
  避免「斜面改高度、顶部箭头被裁」的双真源。

### 2.3 一处偏离你的建议：锚点用 `design` 而不是 `viewport`

本页是中屏上下分区布局（splitV），可视区设计高度实测 736 而预设只有 325。
`anchor: 'viewport'` 的 bottomLeft 原点会钉在**可视区最底部**（设计 y=530.7，比设计稿底边低 205），
场景被压到画面下方、上方留一大片空白（改前 `groundY` 落在 726 中的 620 处）。
`anchor: 'design'` 的原点在预设底边（325），场景落在设计稿内，且比例尺不随窗口缩放漂移 ——
这是教学页更需要的稳定性。量程公式也相应改用 `preset.width/height`。

## 三、`second-law`：手算四舍五入

原值 `physicsHeight: 3.87` 是 `10 × 325 / 840 = 3.869047…` 的截断。实测可视区设计尺寸 840×328.7，
正确值 3.913：

| | scaleX | scaleY | 偏差 |
|---|---|---|---|
| 改前 | 84.00 | 84.94 | 1.1%，告警 |
| 改后 | 84.00 | 84.00 | 0 |

实现上用了 `10 * (vp.designVisibleH / vp.designVisibleW)` 而不是 `10 * 325/840`：
后者只在容器恰好等于预设宽高比时成立，容器一变形就重新失衡；前者对任何容器都精确。

## 四、`newton-second`：锚点模式错配

本页整体画在一个**原始 `<svg>`**（无 `vp.transform`）里，几何与矢量起点全是容器像素 / `originDesign`，
矢量长度只走 `refMagnitudes + maxVectorLength` 归一化，**不经过 `worldToDesign`**。
所以 `scaleX === scaleY === 1` 就够了：`anchor: 'design'` + `physicsWidth/Height = preset` 恒为 1/1
（改前随容器浮动，实测 1 / 1.133）。

## 五、F 标签落进 m₂：端点写反（未动 `VectorArrow`）

`Model0ConnectedBodies.tsx` 整体法视图的 F 起点原为 `origin={model0.ropeRight}`，
即 `m₂_pos.x` = **m₂ 左面**（绳连接点），而隔离 m₂ 视图用的是 m₂ 右面。
旧箭头被假造成 60+ px 时整根捅穿 56 px 的方块，视觉上像「从右面推出」，掩盖了端点错位；
箭头恢复 14.5 px 真实长度后整根落在方块内部，标签也跟着进去了。

改法：`origin={{ x: model0.m2_pos.x + model0.w2, y: groundY + model0.h2 / 2 }}`（与隔离视图一致）。
实测：整体法视图 F 标签已移出 m₂ 右边缘，不再与 `m₂ = 4kg` 重叠。

> 副作用提示：F=15 N 在共用基准（ref = 137.2 N 峰值 / 0.9 = 152.4）下箭长只有 6.6 px，
> 这是「受力分析页所有力共用一把尺」的既定结论（F ≪ G 正是本页要讲的对比），本轮未动。

## 七、新发现：非等比缩放仍有 20 页（建议单开一批）

上一批的扫描脚本只匹配 `refMagnitude` 关键字，所以 `[VectorArrow] 非等比缩放` 这一类一直被漏计。
这次按「全部 warning/error」重扫 124 页：**95 页干净，20 页仍有非等比缩放告警，10 页有其它告警/错误**。

两类成因：

**A 类（11 页）`scaleX === 1`，`scaleY = 1.08 ~ 2.31`** —— 与 `newton-second` 完全同源：
`visibleArea` 风格页面 + `anchor: 'viewport'` + `physicsWidth/Height = preset.width/height`。

```
anim-friction 1 / 2.307      anim-gravity-basic 1 / 1.175
anim-vector-addition 1/1.175 anim-orthogonal-decomposition 1 / 1.175
anim-gravity 1/1.175         anim-work 1 / 1.082
anim-potential-energy 1/1.082   anim-energy-conservation 1 / 1.082
anim-velocity 1/1.082        anim-acceleration 1 / 1.082
anim-uniform-acceleration 1/1.082   anim-connected-bodies 1 / 1.082
```
修法即 `anchor: 'design'` 一行（需逐页确认确实不用 `worldToDesign`）。

**B 类（9 页）真实单位比例尺 + 手写 `physicsHeight`** —— 与 `second-law` 同源：

```
anim-gas-laws 140 / 130、152.6      anim-clapeyron 140 / 130、152.6
anim-nuclear-decay 84 / 50、58.0    anim-saturated-vapor 84 / 81.3、92.1
anim-electrostatic-shielding 84/81.3、95.5   anim-brownian-motion 4.2 / 4.74
anim-doppler-effect 19.5 / 18.1     anim-forced-resonance 100 / 107.9
```
修法：`physicsHeight` 由 `vp.designVisibleH / vp.designVisibleW` 反推（与第 3 项同法）。

**影响不只是告警**：非等比缩放会让**所有矢量方向失真**——`anim-friction` 的 2.31 会把 45° 的力
画成 66.6°、30° 画成 53°，而该页讲的正是摩擦力与合力方向。这一项优先级应高于纯视觉问题。

未直接动手的原因：每页都需先确认「是否有意为之」（`intentionalNonUniformScale` 存在就是给这类场景用的），
且 B 类要确认 `physicsHeight` 的物理含义（物室尺寸 / 世界尺度），不能批量盲改。
