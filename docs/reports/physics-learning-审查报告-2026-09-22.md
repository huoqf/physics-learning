## 一、🔴 P0 必改：会直接形成错误认知的物理错误

### F1 折射动画画反了——光从空气进玻璃，反而"远离法线"

**文件**：`src/features/optics/refraction/RefractionAnimation.tsx:98-112`

```ts
const incDirX = Math.sin(theta1Rad)   // ← 角度从"界面"量起
const incDirY = Math.cos(theta1Rad)
const refDirX = Math.sin(theta2Rad)   // ← 同上
const refDirY = Math.cos(theta2Rad)
```

**为什么错**：该模式界面是**竖直直径**（`:126` 画 `x1=cx → x2=cx`），法线是**水平线**（`:133-139`）。而 `(sinθ, cosθ)` 是以**竖直方向**为基准，等于把角度从界面而非从法线量起，于是：

- 画出的实际入射角 = **90° − θ₁**，界面标示 θ₁=30° 时画面是 60°；
- 折射光线与法线夹角 = 90° − θ₂ = 70.5°，比入射的 60° **更大** —— 画面呈现"疏→密却远离法线"，与折射定律完全相反。

**旁证**：同一文件进阶模式（平行玻璃砖，界面水平、法线竖直）的写法（`:284-300`）是**正确的**，两模式自相矛盾，说明基础模式是转置笔误而非设计。
附带：`:198-212` 的角度弧 `arcPath(cx,cy,arcR, -theta1, 0)` 画在法线右侧/入射光不在的一侧，与真实光线都不重合（学生会看到"角标和光线各说各话"）。

**改法**：基础模式改 `incDirX=cosθ, incDirY=sinθ`（折射同理），并把角度弧改为沿实际入射/折射方向绘制。

### F3 全反射：反射光线射进空气且反射角错误

**同文件** `:35-36`

```ts
const reflectedDirX = -Math.sin(theta1Rad)
const reflectedDirY = incidentDirY      // = -cosθ₁
```

水平界面镜面反射应**保持 x 分量、翻转 y 分量**，即反射后行进方向 `(sinθ₁, +cosθ₁)`（向右下返回水中）。现写法得到的是 `(−sinθ₁, −cosθ₁)`，即**翻转了 x 分量、保留了 y 分量** —— 它恰好是正确的反射方向 `(sinθ₁, +cosθ₁)` 的**反向**（相差 180°），因此反射光射向上方空气侧，反射定律被违反。

> F2 + F3 合起来，这个页面呈现的是"既没有正确的反射，也没有正确的折射"。而"全反射"本身是**新高考Ⅰ/Ⅱ卷高频**（光导纤维、水中看岸），建议优先修。

### F4 玻尔模型轨道半径：画成了 r ∝ n，应为 r ∝ n²

**文件**：`src/features/modern/bohr-theory/hooks/useExcitationSimulation.ts:343-345`

```ts
const maxLvl = 4, baseR = 25
for (let n = 1; n <= maxLvl; n++) {
  const r = (n + 0.6) * baseR      // 25·1.6 / 25·2.6 / 25·3.6 / 25·4.6 → 线性
```

人教版选择性必修三要求 `r_n = n²·r₁`，即 **1 : 4 : 9 : 16**；当前是 1 : 1.625 : 2.25 : 2.875。跃迁箭头的起止半径（`:356`）用同一错误公式。

**自证**：同文件 `:183` 电子角速度用 `0.02 * (1.8 / (lvl*lvl*lvl))`，即 ω ∝ 1/n³ —— 这只有在 **r ∝ n²、v ∝ 1/n** 时才成立。同文件内部就互相打架。

**改法**：`const r = n * n * baseR`（`baseR` 相应调小）。

### F6 热力学第一定律沙箱：W、V、p 三者互不自洽

**文件**：`src/physics/firstLaw.ts:269`（及 `:70-73`）

```ts
const V = 1.0e-3 - 1.0e-6 * W        // 体积随做功"线性映射"
const P = T / (3 * V)                // nR = 1/3
```

`C_SYS = 0.5`（`:17`）。取 W=100 J 绝热压缩：ΔU=100 → ΔT=200 K → T=500 K、V=9×10⁻⁴ m³、P≈1.85×10⁵ Pa。
而这个过程真实的准静态功积分 `∫p dV` 只有 **约 11 J**（ adiabatic 解算 T 应只升到 ~322 K，ΔT≈22 K）。**标称做功 100 J 的画面，物理上对应 11 J，差一个数量级。**

危害很直接：高考热力学计算题的核心方法就是"p–V 图面积 = 功"，学生会在这里看到 W=100 J 而图上面积只有 10 几焦。

另一小问题：同一体积在两种模式下活塞高度差 2 倍 —— 沙箱 `pistonY = 3.2 - (W/500)*1.5`（`:72`）vs 循环 `pistonY = 3.2 + ((V-1e-3)/1e-3)*1.5`（`:70`）。

**改法**：要么按真实过程由 V 反解 W 并反过来驱动滑块，要么明确标注"此模式下数值为示意，不可用于定量计算"（推荐前者）。

## 四·B｜专项核查：中屏布局、坐标系与三屏同步

> 针对第三次追问："布局/preset 改过几次会不会留下问题？viewport 与坐标变换是否正确、能否保证物理？三屏是否同步？"
> **结论先行：改过 4 次（其中 1 次是补丁式），但 Viewport 架构收口做得不错，当前几何是正确的 —— 真问题不是"现在错了"，而是"缺一道类型防线，下一次改还会错"。**

### 4B.1 变更史还原（你的怀疑成立）

| 提交 | 日期 | 改动 | 性质 |
|---|---|---|---|
| `171ffdc` | 2026-06-03 | 三屏布局**由写死像素改为响应式** | 架构调整 |
| `390aa6e` / `b6c2e5e` | 2026-07-08 | PageLayout 统一页面容器 + **Viewport 架构统一** | 架构调整 |

| `3849c12` | — | 完成 `presetCompensation` 1.2 迁移 | 补丁收尾 |

**这次变更的两个危险特征**已核实：
1. **非等比**：宽 ×1.2，**高度完全没动**（650 / 325 保持原值）。若下游有任何"宽高各自缩放"的地方，圆形轨道会立刻变成椭圆。
2. **手工逐个放大**：`20+ 组件硬编码坐标同步缩放（×1.2）` —— 逐处手工 ×1.2，属于典型的 patching（正是需要警惕的做法），后续 `c59e05c` 的"布局跳变"就是它留下的尾巴。

### 4B.2 现在为什么没炸 —— Viewport 层把非等比吸收了

核查的核心是：**第 3 次改动的非等比是否被隔离在一层内**。答案是：是。

```ts
// src/utils/useViewport.ts
scale     = min(visibleW/designW, visibleH/designH) × compensation   ← 单一标量
transform = translate(tx ty) scale(scale)                            ← 单一等比
```

`useSceneScale` 的输出单位也被收口为**设计坐标（design-unit）**（文件头 JSDoc 明示），`AnimationSvgCanvas` 再把 `<g transform={vp.transform}>` 套在最外层。于是：

> **preset 从 700×650 改成 840×650 这件事，对场景内部完全不可见。** 场景只关心"design 坐标 0..840 / 0..650"，至于它最终被缩放到多少 CSS 像素，由 vp.transform 一个地方决定。

**因此：圆还是圆，正方形还是正方形，抛体轨迹、圆周运动、v-t 图的几何形状不会因为那次 ×1.2 而失真。** 这是架构做对的地方（单一职责 + 坐标收口），应当保留。

顺带核实：`BulletBlockAnimation.tsx:20` 的 `DESIGN_WIDTH = CANVAS_PRESETS.splitV.width` —— **从 preset 派生而非硬编码**，所以自动跟随迁移 ✓；且 `:53` 显式 `scaleY: scaleX` 保证一维场景等比 ✓。`BoundaryMagneticField/SimulationView.tsx:98-103` 用 `worldToDesign → designToPixel` 两步转换 —— **可作为混合渲染的正确范例** ✓。

### 4B.4 三屏同步 —— 基本同步，但播放时有 ≤0.05s 相位差

**核查结论：✅ 基础同步成立。** 三屏全部订阅**同一个 zustand store** 的同一份 `time` / `params`，无独立计时器，因此不存在"各屏各跑一个循环"的问题：

| 屏 | 取数位置 | 是否同一源 |
|---|---|---|
| 中屏动画 | `AnimationPage.tsx:43-48` `useAnimationStore(...)` 取 `time/isPlaying/speed/params` | ✅ |
| 右侧物理量面板 | `AnimationPage.tsx:228-229` `useAnimationStore(s => s.time)` | ✅ |
| 左侧参数面板 | `AnimationPage.tsx:319-322`（低频订阅，刻意不看 `time`） | ✅ 设计如此，避免参数区随帧重渲染 |

**⚠️ 唯一例外 —— `AnimationPage.tsx:242`**

```ts
// 播放时用 0.1s 精度减少重算，拖动时用精确时间保持响应
const effectiveTime = isPlaying ? Math.round(time * 10) / 10 : time
```

即：**中屏动画用连续 `time`，右侧数值面板用量化到 0.1s 的 `effectiveTime`**。后果是播放过程中，右侧实时读数与中屏画面之间存在**最多 0.05 s 的相位差**。

- 暂停时不生效（三元表达式在 `isPlaying=false` 走精确分支）→ **静态读数准确** ✓
- 但"边播放边读 v-t 图某点数值"这类训练会偏。考虑到 2026 命题强调"**从物理图像获取信息的能力**"（官方评析原话），建议：**播放态至少提升到 0.02 s 精度**，或仅在实测掉帧时才降级精度。
- 这个取舍本身是合理的性能手段，**不建议删除**，只建议调高精度 + 在 UI 上不做"这是同一时刻精确读数"的暗示。
